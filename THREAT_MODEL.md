# Модель угроз

## Модель продукта

Веб-сервис предназначен для управления клубным членством в спортивном клубе. Пользователь может авторизоваться в системе, оформить абонемент, продлить его, посмотреть срок действия и оформить заморозку.

Основные компоненты системы:

- веб-интерфейс пользователя;
- серверная часть приложения (backend/API);
- база данных;
- механизм регистрации и авторизации пользователей.

Основные потоки данных:

1. Пользователь отправляет данные через веб-интерфейс.
2. Веб-интерфейс передаёт запрос серверной части.
3. Сервер проверяет права пользователя и корректность запроса.
4. Сервер получает или изменяет данные в базе данных.
5. Результат операции возвращается пользователю.

Основные точки входа:

- форма входа и регистрации;
- запросы на просмотр данных абонемента;
- оформление абонемента;
- продление абонемента;
- оформление заморозки.

**Что уже существует:**

- веб-интерфейс сервиса;
- базовая серверная часть;
- работа с данными пользователей и абонементов;

**Что пока планируется:**

- дополнительная проверка входных данных;
- просмотр срока действия абонемента;
- оформление и продление абонемента;
- оформление заморозки.
- улучшение обработки ошибок и защиты API.

**Существенные допущения:**

- пользователь может изменять только собственный абонемент;
- прямой доступ пользователя к базе данных отсутствует;
- все изменения данных выполняются через серверную часть;
- соединение между пользователем и сервисом предполагается защищённым с помощью HTTPS;
- внешняя платёжная система в данной модели не рассматривается;
- административные функции управления спортивным клубом находятся вне рассматриваемой функциональности.

## Границы доверия

| Граница | Что пересекает | Почему требуется проверка |
| --- | --- | --- |
| Пользователь -> веб-приложение | Логин, пароль, данные запросов | Пользователь может передать некорректные или специально изменённые данные |
| Веб-интерфейс -> backend/API | Запросы на просмотр и изменение абонемента | Нельзя считать запрос доверенным только потому, что он пришёл от интерфейса приложения |
| Backend -> база данных | Данные пользователей и абонементов, команды чтения и изменения | Необходимо контролировать корректность запросов и не допускать несанкционированного изменения данных |
| Неавторизованный пользователь -> защищённые функции | Запросы к данным абонемента и операциям продления/заморозки | Необходимо убедиться, что пользователь прошёл авторизацию и имеет право выполнять операцию |

## Значимые объекты и свойства

Основными значимыми объектами системы являются:

- **Учётная запись пользователя** - должна быть доступна только её владельцу
- **Данные абонемента** - тип абонемента, дата начала и дата окончания должны изменяться только через разрешённые операции
- **Статус заморозки** - пользователь не должен иметь возможности самостоятельно устанавливать произвольный срок или обходить ограничения системы
- **Сессия пользователя** - должна однозначно определять авторизованного пользователя и не должна использоваться другим человеком
- **Персональные данные пользователя** - не должны быть доступны другим пользователям

Нарушение целостности этих объектов может привести к получению бесплатного или более длительного абонемента, обходу ограничений заморозки или изменению чужих данных.

Нарушение конфиденциальности может привести к раскрытию данных другого пользователя.

### Требования безопасности

- **SR-01** - пользователь должен получать доступ только к собственным данным.
- **SR-02** - защищённые операции должны быть доступны только после авторизации.
- **SR-03** - сервер должен проверять входные данные независимо от проверок на стороне веб-интерфейса.
- **SR-04** - пользователь не должен иметь возможности самостоятельно задавать недопустимые даты и состояния абонемента.
- **SR-05** - запросы к базе данных должны выполняться безопасным способом без возможности внедрения произвольных SQL-команд.
- **SR-06** - данные авторизации и сессии не должны передаваться или храниться в открытом виде.
- **SR-07** - ошибки приложения не должны раскрывать внутреннюю структуру системы или базы данных.

## Приоритетный набор

В приоритетный набор включены угрозы:

**T-01, T-02, T-03, T-04, T-05 и T-07.**

Они выбраны потому, что непосредственно связаны с основными функциями сервиса и могут привести к наиболее существенным последствиям: доступу к чужому абонементу, изменению его состояния, обходу ограничений приложения, несанкционированному доступу к аккаунту или данным базы.

Угрозы T-06 и T-08 также учитываются, однако имеют более низкий приоритет, поскольку их непосредственные последствия для основных данных системы меньше.
