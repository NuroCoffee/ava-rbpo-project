# Паспорт проекта

## Общие сведения

**Название команды:** *АВА*  
**Название продукта:** *Клубное членство спортзала*  
**Коды участников:** `M1`, `M2`, `M3`  

## 1. Назначение

Веб-сервис предназначен для управления клубным членством в спортивном клубе: оформления и продления абонементов. Клиенты получают возможность отслеживать срок действия абонемента, а сотрудники клуба - управлять членством и контролировать использование услуг. Предметная логика приложения включает расчёт срока действия абонементов, заморозку членства и проверку доступности занятий в соответствии с условиями выбранного тарифа.

## 2. Граница продукта

**В продукт входит:**

- Регистрация и авторизация клиентов и сотрудников клуба.
- Просмотр тарифов и оформление клубного членства.
- Учёт абонементов: срок действия, продление и заморозка.
- Регистрация посещений сотрудником клуба с проверкой действительности абонемента.
- Личный кабинет клиента с информацией об абонементе и истории посещений.
- Управление тарифами и абонементами со стороны администратора клуба.

**Внешнее окружение и внешние системы:**

- Веб-браузеры клиентов и сотрудников, через которые осуществляется доступ к сервису.
- Работа сотрудников клуба на стойке регистрации: сотрудник проверяет личность посетителя и вносит сведения о посещении в сервис.
- Оплата абонементов производится вне сервиса.

**Команда сознательно не реализует:**

- Приём онлайн-платежей и возврат денежных средств.
- Интеграцию с турникетами.
- Составление тренировочных программ и планов питания.
- Расчёт заработной платы сотрудников и бухгалтерский учёт.
- Отдельное мобильное приложение.

## 4. Сквозные сценарии

### Сценарий 1. Оформление абонемента клиентом

- **Участники:** клиент клуба
- **Начальное условие:** клиент клуба зарегистрировал аккаунт в системе и авторизовался
- **Основные действия:** просматривает доступные варианты абонемента, выбирает подходящий вариант, оформляет абонемент, оплачивает абонемент через сторонние сервисы
- **Результат:** у клиента клуба появляется действующий абонемент
- **Какие данные или состояние изменяются:** у клиента клуба создаётся действующий абонемент

### Сценарий 2. Заморозка абонемента

- **Участники:** клиент клуба
- **Начальное условие:** клиент вошёл в систему и имеет действующий абонемент, тариф которого допускает заморозку.
- **Основные действия:** клиент открывает свой абонемент, выбирает даты заморозки и подтверждает запрос. Система проверяет, что выбранный период не пересекается с другой заморозкой и не превышает доступный лимит дней. При успешной проверке система сохраняет период заморозки, иначе сообщает причину отказа.
- **Результат:** заморозка оформлена; в выбранный период посещения по абонементу недоступны, а срок его действия продлевается на количество дней заморозки.
- **Какие данные или состояние изменяются:** сохраняется период заморозки, уменьшается остаток доступных дней заморозки и переносится дата окончания абонемента. При отказе данные не изменяются.

### Сценарий 3. Посещение клуба по абонементу


- **Участники:** клиент клуба, сотрудник клуба.
- **Начальное условие:** клиент пришёл в клуб и предъявил сотруднику идентификатор своего абонемента; сотрудник вошёл в систему.
- **Основные действия:** сотрудник находит абонемент по идентификатору и нажимает «Отметить посещение». Система проверяет срок действия абонемента, отсутствие заморозки и остаток посещений. Если проверка пройдена, система регистрирует посещение, сотрудник пропускает клиента, и тот идёт заниматься. Если проверка не пройдена, система сообщает причину отказа.
- **Результат:** клиент допущен к тренировке либо получил объяснение, почему воспользоваться абонементом нельзя.
- **Какие данные или состояние изменяются:** при допуске сохраняется запись о посещении с датой и временем. У абонемента с ограниченным количеством посещений списывается одно посещение; у безлимитного фиксируется только факт визита.

## 5. Значимые данные и другие объекты

| Данные или объект | Для кого имеют значение | Последствия раскрытия | Последствия неправильного изменения, удаления или недоступности |
| --- | --- | --- | --- |
| Персональные данные клиентов: ФИО, телефон, электронная почта | Клиенты, сотрудники клуба | Посторонние могут использовать контакты для спама, мошеннических сообщений и звонков от имени клуба | Сотрудник не сможет найти клиента или связаться с ним; уведомления могут отправляться другому человеку |
| Данные абонементов: владелец, тариф, срок действия, остаток посещений, периоды заморозки | Клиенты, сотрудники и администратор клуба | Посторонние узнают, какими услугами пользуется конкретный клиент и когда действует его членство | Клиенту могут отказать в оплаченном посещении либо предоставить неоплаченный доступ; возможны ошибочные списания посещений |

## 6. Компоненты и внешние взаимодействия

- Веб-клиент: страницы в браузере для клиентов, сотрудников и администратора. Позволяет просматривать тарифы и абонементы, подавать заявки, регистрировать посещения и управлять членством.
- Сервер приложения: обрабатывает запросы, проверяет полномочия пользователей, оформляет абонементы, проверяет возможность посещения, списывает посещения и рассчитывает условия заморозки.
- База данных: хранит пользователей, роли, тарифы, абонементы, заявки, периоды заморозки и историю посещений.
Основные взаимодействия:
- Браузер передаёт серверу данные форм: сведения для входа и регистрации, выбранный тариф, идентификатор абонемента и даты заморозки.
- Сервер проверяет данные и права пользователя, читает и изменяет записи в базе данных.
- Сервер возвращает браузеру страницы с результатами операций или сообщениями об ошибках.
- При регистрации посещения запись о визите и списание посещения выполняются в одной транзакции, чтобы остаток соответствовал истории.
Отдельные фоновые процессы для первой версии не требуются: срок действия и наличие заморозки проверяются при обращении к абонементу. Внешние интеграции не предусмотрены. Оплата проходит вне сервиса, сотрудник вручную подтверждает её получение.

## 7. Откуда продукт получает данные

Продукт получает данные из HTTP-запросов пользователей и сотрудников клуба, а также из собственного сохранённого состояния в PostgreSQL. Внешние сервисы напрямую данные в приложение не передают.

| Источник | Пример данных | Кто управляет источником | Как продукт использует данные |
| --- | --- | --- | --- |
| Регистрация и вход | Электронная почта, пароль | Гость или зарегистрированный пользователь | Создание учётной записи и установление личности пользователя |
| Клиентские API-запросы | Выбранный тариф, запрос на оформление или продление, даты заморозки | Клиент клуба | Выполнение разрешённых клиентских сценариев и проверка предметных ограничений |
| Запросы сотрудника клуба | Идентификатор клиента, выбранный тариф, команда выдачи абонемента или регистрации посещения | Сотрудник клуба | Оформление членства и регистрация посещений после проверки полномочий и состояния абонемента |
| Административные API-запросы | Параметры тарифа и другие административные команды | Администратор клуба | Управление настройками и объектами, доступными административной роли |
| Контекст аутентификации | Идентификатор текущего пользователя и данные его авторизованного состояния | Формируется сервером после успешной аутентификации | Определение текущего пользователя и последующая проверка его полномочий |
| PostgreSQL | Пользователи, роли, тарифы, абонементы, история посещений и связанные состояния | Приложение | Получение текущего состояния продукта и сохранение результатов предметных операций |
| Системное время сервера | Время выдачи абонемента и регистрации посещения | Серверное окружение | Расчёт срока действия абонемента и фиксация времени предметных событий |
| Проверка оплаты и личности вне сервиса | Результат проверки оплаты или личности клиента | Сотрудник клуба | Сотрудник использует результат внешней проверки при выполнении разрешённой операции; прямой интеграции с платёжной системой нет |

Файлы от пользователей, сообщения из брокеров и данные сторонних API в текущей версии продукта не используются.

## 8. Минимальное функциональное ядро

**Обязательные функции:**

- Регистрация, вход и разграничение прав клиента, сотрудника и администратора.
- Просмотр тарифов и управление ими со стороны администратора.
- Подача заявки на оформление или продление абонемента.
- Оформление и продление абонемента сотрудником после подтверждения оплаты.
- Просмотр клиентом своего абонемента и истории посещений.
- Регистрация посещения сотрудником с проверкой срока действия, заморозки и остатка посещений.
- Списание одного посещения для абонементов с ограниченным количеством визитов.
- Заморозка абонемента с проверкой лимита дней и пересечения периодов, пересчёт даты окончания.

**Функции, которые можно исключить при нехватке времени:**

- Графики и сводные отчёты о посещаемости.
- Выгрузка истории посещений в файл.
- Отображение QR-кода абонемента: сотрудник сможет находить его по идентификатору.
- Расширенные фильтры и сортировка списков.
- Настройка оформления личного кабинета.

После удаления необязательных функций должны сохраняться собственная серверная предметная логика, два-три основных сценария, различимые полномочия и значимые данные.

## 9. Стек и путь к первой работающей версии

**Основные технологии:**

- Python 3.12 или новее - язык разработки серверной части.
- FastAPI - HTTP API, обработка запросов, валидация входных данных и автоматическая документация OpenAPI.
- Uvicorn - ASGI-сервер для локального запуска и развёртывания приложения.
- Pydantic - описание и проверка входных и выходных моделей API.
- PostgreSQL - основная реляционная база данных.
- SQLAlchemy - работа с моделями и запросами к базе данных.
- Alembic - управление изменениями структуры базы данных.
- JWT - механизм аутентификации пользователей и передачи информации о пользовательской сессии.
- Argon2id - хеширование паролей пользователей.
- Pytest и HTTPX - автоматическое тестирование прикладной логики и HTTP API.
- Ruff - статическая проверка и единое форматирование Python-кода.
- Docker Compose - воспроизводимый локальный запуск приложения и PostgreSQL.

Docker Compose - планируется для воспроизводимого совместного запуска приложения и PostgreSQL; текущая версия поддерживает локальный запуск приложения с установленным PostgreSQL.

**Технологии, новые для команды:**  
Существенно новых для команды технологий нет; участники знакомы с выбранным стеком или имеют опыт работы с аналогичными инструментами.

**Архитектурный подход:**  
Сервер реализуется как модульный монолит. Предметные модули разделены на API, прикладные сценарии, доменные правила и инфраструктурные адаптеры.

Текущие предметные модули:
- аутентификация и пользователи;
- роли и полномочия;
- типы абонементов;
- абонементы клиентов;
- посещения.

Планируемое развитие предметной модели:
- заморозка абонементов.
- зоны фитнес-клуба;
- правила доступа тарифа к зонам;
- проверка возможности доступа клиента в выбранную зону;


**Внешние сервисы, необходимые для запуска:**  
Для полноценной работы проекта обязателен только PostgreSQL. Другие внешние сервисы и сторонние API не используются.

**Как основные сценарии будут запускаться и проверяться при недоступности внешних сервисов:**  
Единственная обязательная внешняя зависимость - PostgreSQL. При недоступности базы данных сервер остаётся запущенным, но операции, требующие чтения или изменения данных, возвращают контролируемую ошибку `503 Service Unavailable`. Отдельный liveness-endpoint позволяет проверить, что процесс приложения работает, а readiness-endpoint показывает готовность приложения обслуживать основные запросы и возвращает ошибку, если соединение с PostgreSQL отсутствует.

Предметная логика дополнительно проверяется автоматическими модульными тестами без запуска PostgreSQL за счёт отделения доменных правил от инфраструктурного слоя. Интеграционные и API-тесты, проверяющие сохранение данных и транзакции, выполняются с тестовым экземпляром PostgreSQL.

**Что команда реализует первым, чтобы получить запускаемую версию:**  

Первая запускаемая техническая основа проекта уже реализована: FastAPI-приложение запускается локально, подключается к PostgreSQL, схема данных управляется Alembic, а /api/v1/health/live и /api/v1/health/ready позволяют проверить процесс приложения и доступность хранилища.

Текущая предметная реализация включает:

- приложение запускается локально;
- устанавливается соединение с PostgreSQL;
- миграции создают начальную структуру базы данных;
- `GET /api/v1/health/live` и `GET /api/v1/health/ready` для проверки доступности;
- Swagger UI позволяет просматривать и вручную вызывать доступные API-методы;
- реализована регистрация и вход пользователей;
- настроено разграничение ролей клиента, сотрудника и администратора;
- включена работа с тарифами, выдача и просмотр абонементов;
- есть регистрация посещений и просмотр их истории.

Следующие этапы включают:
- полноценные сценарии заявки и продления абонемента;
- заморозка абонемента;
- расширение административных операций;
- воспроизводимый запуск приложения вместе с PostgreSQL через Docker Compose;
- веб-интерфейс.

## 10. Локальный запуск

**Требования к окружению:**

Для текущего способа локального запуска необходимы:

- Git;
- Python 3.12 или новее;
- PostgreSQL, запущенный локально;
- pip;
- свободный порт 8000 для HTTP API;

Совместный запуск приложения и PostgreSQL через Docker Compose планируется добавить позднее и не является обязательным для текущей версии.

**Команды установки и запуска:**

Получить проект:

```bash
git clone https://github.com/NuroCoffee/ava-rbpo-project.git
cd ava-rbpo-project/product
```

Создать виртуальное окружение и установить зависимости:
```bash
python3 -m venv .venv
source .venv/bin/activate
python -m pip install -e ".[dev]"
```

Создать файл локальной конфигурации:

```bash
cp .env.example .env
```

Пример конфигурации:

```env
APP_NAME=AVA Gym Club Membership
APP_ENV=local
APP_DEBUG=false
DATABASE_URL=postgresql+psycopg://postgres:postgres@localhost:5432/ava_club
JWT_SECRET_KEY=change-this-local-secret-key
JWT_ACCESS_TOKEN_TTL_MINUTES=30
```

Перед запуском необходимо создать базу данных ava_club либо изменить DATABASE_URL в соответствии с параметрами существующего PostgreSQL.

Применить миграции базы данных:

```bash
alembic upgrade head
```

При необходимости создать администратора и сотрудника для ручной проверки:
```bash
python -m club_service.cli create-admin --email admin@example.com
python -m club_service.cli create-employee --email employee@example.com
```

Запустить приложение:
```bash
uvicorn club_service.main:app --reload --env-file .env
```

После запуска приложение доступно по адресу:

```text
http://127.0.0.1:8000
```

**Команда или запрос для проверки:**

Проверка работы серверного процесса:

```bash
curl.exe -i http://127.0.0.1:8000/api/v1/health/live
```

Дополнительно можно проверить готовность приложения и соединение с PostgreSQL:

```bash
curl http://127.0.0.1:8000/api/v1/health/ready
```

При корректно запущенном приложении и доступной базе данных запрос к readiness-endpoint возвращает HTTP `200`:

```json
{
  "status": "ready",
  "database": "ok"
}
```

Если PostgreSQL недоступен, процесс приложения продолжает работать: /health/live остаётся успешным, а /health/ready возвращает 503 Service Unavailable.

Успешный локальный запуск подтверждается тем, что приложение стартует без необработанных ошибок, миграции применяются, liveness- и readiness-проверки возвращают ожидаемый результат, а Swagger UI открывается и отображает API приложения.

Docker Compose планируется как дополнительный воспроизводимый способ запуска на следующих этапах проекта.
