# Проектные решения безопасности

Документ фиксирует основные проектные решения безопасности сервиса клубного членства спортзала.

Будущие проверки ниже описывают план проверки механизма и не являются уже выполненными свидетельствами.

Актуальное описание продукта, ролей и сценариев приведено в [PROJECT.md](./PROJECT.md).

## D-01. Централизованная аутентификация и ролевая авторизация

**Контекст:**  
HTTP-клиент находится за границей доверия. Пользователь может напрямую вызвать защищённый endpoint, попытаться выполнить операцию другой роли либо передать изменённые данные аутентификации.

**Решение:**  
Аутентификация и проверка роли выполняются сервером до выполнения защищённой предметной операции.

После получения JWT сервер проверяет его корректность и срок действия, определяет пользователя и загружает его актуальное состояние из PostgreSQL. Роль для принятия решения о доступе берётся из серверных данных, а не из параметров клиентского запроса.

Для проверки полномочий используются общие зависимости:

- `get_current_user`;
- `require_client`;
- `require_employee`;
- `require_admin`.

Клиент не может самостоятельно назначить себе роль. Администратор может выполнять разрешённые операции сотрудника.

**Обоснование:**  
Проверки только в веб-интерфейсе недостаточно, поскольку любой HTTP-запрос можно сформировать вручную. Централизованная серверная проверка позволяет одинаково устанавливать личность пользователя и его полномочия перед выполнением предметной логики.

Проверка данных аутентификации не позволяет получить полномочия другой роли простой подменой их содержимого.

**Связанные угрозы:** `T-01`, `T-03`, `T-08`.

**Связанные требования:** `SR-01`, `SR-02`, `SR-07`.

**Будущая проверка:**

- **Условие:** существуют клиент, сотрудник и администратор; для них доступны действительные данные аутентификации.
- **Действие:** выполнить защищённый запрос без аутентификации; клиентом вызвать функцию сотрудника; сотрудником вызвать административную функцию; выполнить запрос с изменёнными или недействительными данными аутентификации.
- **Ожидаемый результат:** неаутентифицированный запрос отклоняется; пользователь без требуемых полномочий получает отказ без изменения данных; изменённые или недействительные данные аутентификации не позволяют установить чужую личность или роль; разрешённые операции выполняются.

**Ограничения и последствия:**  
Каждый новый защищённый endpoint должен использовать соответствующий общий механизм проверки доступа. Добавление маршрута без такой проверки нарушит гарантию решения.

## D-02. Авторизация доступа к конкретным объектам

**Контекст:**  
Успешная аутентификация и наличие роли клиента сами по себе не дают право работать с данными другого клиента. Пользователь может изменить идентификатор в HTTP-запросе и попытаться получить чужой абонемент, персональные данные или историю посещений.

**Решение:**  
Для операций с собственными данными сервер определяет владельца по текущему аутентифицированному пользователю, а не принимает его идентификатор как доверенный параметр.

Для клиентских ресурсов используются маршруты вида:

- `/users/me`;
- `/memberships/me`;
- `/visits/me`.

Операции, в которых можно указать произвольного клиента, доступны только сотруднику или администратору в соответствии с их полномочиями.

**Обоснование:**  
Знание идентификатора объекта не подтверждает право доступа к нему. Использование установленной сервером личности вместо переданного клиентом владельца исключает зависимость решения о доступе от подменяемого параметра запроса.

Ролевая авторизация из `D-01` и объектная авторизация решают разные задачи: первая определяет допустимые функции роли, вторая - допустимые конкретные объекты.

**Связанные угрозы:** `T-02`.

**Связанные требования:** `SR-01`, `SR-03`.

**Будущая проверка:**

- **Условие:** существуют клиенты `A` и `B`, имеющие разные абонементы и историю посещений.
- **Действие:** от имени клиента `A` попытаться получить данные клиента `B`, изменяя известные идентификаторы; затем запросить собственные данные `A`.
- **Ожидаемый результат:** клиент `A` не получает персональные данные, абонемент или посещения клиента `B`; собственные разрешённые данные доступны; отказ не изменяет состояние объектов.

**Ограничения и последствия:**  
При добавлении нового способа получения пользовательского объекта необходимо отдельно определить правило его принадлежности и доступа. Проверка только роли не заменяет объектную авторизацию.

## D-03. Серверное управление состоянием и транзакционное выполнение предметных операций

**Контекст:**  
Пользователь полностью контролирует внешний запрос и может попытаться передать собственные значения срока действия, остатка посещений, состояния абонемента или периода заморозки.

Регистрация посещения одновременно изменяет историю посещений и состояние абонемента. Повторный или конкурентный запрос не должен приводить к несогласованному состоянию.

При сбое во время составной операции не должна сохраняться только часть изменений.

**Решение:**  
Критические значения состояния определяются сервером на основании текущих данных и предметных правил.

При выдаче абонемента сервер самостоятельно определяет срок действия, начальный остаток посещений и состояние. Внешний запрос не позволяет непосредственно установить защищаемые внутренние поля.

Допустимые значения дополнительно ограничиваются входными моделями и ограничениями PostgreSQL.

Регистрация посещения выполняется следующим образом:

1. загружается и блокируется изменяемый абонемент;
2. после получения блокировки повторно проверяется его действительность и остаток посещений;
3. создаётся запись о посещении;
4. при ограниченном тарифе остаток уменьшается ровно на одно;
5. связанные изменения фиксируются одной транзакцией.

Для повторной отправки операции используется `idempotency_key`, уникальность которого также закреплена в PostgreSQL. Повтор запроса с тем же ключом не создаёт второе посещение и не выполняет повторное списание.

Для заморозки применяется тот же принцип: клиент передаёт требуемый период, а допустимость периода, пересечения, лимиты и итоговое изменение абонемента определяются сервером.

**Обоснование:**  
Клиентские ограничения интерфейса не являются защитой, поэтому конечное состояние должно определяться серверной предметной логикой.

Транзакция обеспечивает правило «либо сохраняются все связанные изменения, либо ни одно». Блокировка изменяемой записи позволяет принимать решение по актуальному состоянию при конкурентных операциях.

Идемпотентность дополнительно защищает от повторной обработки одного и того же запроса, например после повторной отправки клиентом.

**Связанные угрозы:** `T-04`, `T-05`, `T-06`.

**Связанные требования:** `SR-04`, `SR-05`, `SR-06`, `SR-08`.

**Будущая проверка:**

- **Условие:** существует действующий ограниченный абонемент с известным остатком посещений; подготовлены допустимые и недопустимые значения предметных параметров.
- **Действие:** попытаться передать защищаемые поля напрямую; зарегистрировать посещение; повторить его с тем же `idempotency_key`; выполнить конкурентные операции над одним абонементом; после реализации заморозки передать пересекающийся период и период сверх лимита; отдельно вызвать сбой до завершения составной операции.
- **Ожидаемый результат:** недопустимые значения не меняют состояние; одно успешное посещение создаёт ровно одну запись и уменьшает остаток ровно на одно; повтор с тем же ключом не выполняет изменение повторно; конкурентная обработка не создаёт недопустимого состояния; при сбое связанные изменения либо фиксируются совместно, либо не сохраняются; недопустимая заморозка отклоняется без изменения абонемента.

**Ограничения и последствия:**  
Блокировки увеличивают время ожидания конкурентных операций над одним объектом, поэтому транзакции должны оставаться короткими.

Механизм заморозки пока является направлением дальнейшей реализации; его будущая проверка не является выполненным тестом.

## D-04. Явные модели ответов и контролируемая обработка ошибок хранилища

**Контекст:**  
API может случайно раскрыть пароль, его хранимое представление или другие данные аутентификации при прямой сериализации внутренних объектов либо при возврате подробной внутренней ошибки.

Кроме того, отказ PostgreSQL не должен приводить к ложному сообщению об успешном сохранении данных.

**Решение:**  
Входные и выходные модели API отделены от моделей хранения. В ответ включаются только явно предусмотренные поля.

Пароль и его хранимое представление не входят в модели пользовательских ответов. Внутренние объекты базы данных не возвращаются клиенту напрямую.

Ошибки работы с хранилищем преобразуются в контролируемый ответ без SQL-запроса, traceback, строки подключения и других внутренних данных. Незавершённая транзакция при ошибке не считается успешной.

Для проверки состояния приложения используются раздельные технические endpoint:

- `/health/live` проверяет работу процесса приложения;
- `/health/ready` проверяет доступность обязательного хранилища.

**Обоснование:**  
Явное перечисление разрешённых полей ответа уменьшает вероятность случайного раскрытия нового внутреннего поля после изменения модели хранения.

Обработка инфраструктурной ошибки на границе API позволяет не раскрывать детали реализации и не выдавать ошибочно успешный результат операции, которая не была сохранена.

Раздельные liveness и readiness проверки позволяют отличать работающий процесс от приложения, готового выполнять операции с данными.

**Связанные угрозы:** `T-06`, `T-07`.

**Связанные требования:** `SR-07`, `SR-08`.

**Будущая проверка:**

- **Условие:** существует пользователь с учётными данными и работающая PostgreSQL.
- **Действие:** запросить пользовательские данные обычными API-операциями; вызвать контролируемую внутреннюю ошибку; затем сделать PostgreSQL недоступной и выполнить `/health/live`, `/health/ready` и операцию, требующую данных.
- **Ожидаемый результат:** пользовательские ответы не содержат пароль или его хранимое представление; ответ при внутренней ошибке не раскрывает внутренние технические данные; при недоступности хранилища `/health/live` подтверждает работу процесса, `/health/ready` показывает неготовность приложения, а бизнес-операция не сообщает о незафиксированном изменении как об успешном.

**Ограничения и последствия:**  
При добавлении нового поля внутренней модели необходимо отдельно определить, допустимо ли возвращать его через API. Контролируемая обработка пользовательского ответа не заменяет отдельную политику доступа к серверным журналам.

# Покрытие угроз

| Угроза | Связанные SR | Решение |
| --- | --- | --- |
| `T-01` - доступ к защищённому API без аутентификации | `SR-01` | `D-01` |
| `T-02` - получение чужих данных через подмену идентификатора | `SR-01`, `SR-03` | `D-02` |
| `T-03` - вызов функции более привилегированной роли | `SR-02`, `SR-04` | `D-01` |
| `T-04` - подмена параметров и состояния абонемента | `SR-04`, `SR-06` | `D-03` |
| `T-05` - повторная или конкурентная регистрация посещения | `SR-05` | `D-03` |
| `T-06` - частичное состояние при сбое PostgreSQL | `SR-05`, `SR-08` | `D-03`, `D-04` |
| `T-07` - раскрытие аутентификационных данных через API | `SR-07` | `D-04` |
| `T-08` - подделка данных аутентификации и роли | `SR-02`, `SR-07` | `D-01` |

Для выбранного приоритетного набора `T-02`, `T-03`, `T-04`, `T-05`, `T-06` прослеживается цепочка:

```text
T → SR → D → будущая проверка
```
